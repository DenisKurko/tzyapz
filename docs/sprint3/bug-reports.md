## BUG-001 — Вхід із неправильним паролем відкриває кабінет іншого клієнта (John Smith)

**Severity:** Critical  **Priority:** P3  **Status:** Rejected (не відтворюється)
**Linked:** test case TC-014; requirement F-20 (також S-20)

> **Повторна перевірка 11.11.2026 (Run 2):** TC-014: неправильна пара логін/пароль → «The username and password could not be verified.», вхід не виконано. Дефект не відтворюється, тому звіт переведено в Rejected. Спостерігався лише 09.11.2026 до скидання даних demo.

### Description
F-20 (SRS 1.1): якщо пара логін/пароль не відповідає жодному обліковому запису, система показує сторінку з повідомленням «Логін або пароль не підтверджено», а вхід не виконується. Фактично будь-яка **непорожня** неправильна пара виконує вхід у кабінет іншого клієнта — John Smith — з його дев'ятьма рахунками. Перевірено дві пари: `galtechfintech` / `wrong_pass123` (існуючий логін, хибний пароль) і `nobody_zz_9174` / `qq` (неіснуючий логін), а також ручним набором і заповненням через скрипт. Порожній пароль обробляється правильно: «Please enter a username and password.».
Severity Critical: стороння особа бачить чужі фінансові дані й може виконувати операції від чужого імені, тобто це серйозний витік даних і обхід автентифікації. Priority P3 за 4.13: подальше виконання кейсів не блокується.

**Відтворюваність: нестабільна.** До 21:17 UTC дефект відтворювався 3 з 3 разів (20:40–20:43 UTC). Після того як demo скинуло дані (09.11.2026 ≈ 21:17 UTC, рахунки почали нумеруватися з 13455), ті самі кроки дали правильний результат: о 21:21 UTC для `nobody_zz_9174` / `qq` показано «Error! The username and password could not be verified.», вхід не виконано. Тобто дефект проявляється лише в певному стані даних спільного demo. Точну умову встановити не вдалося: для цього довелося б змінювати налаштування Admin Page, а це заборонено п. 5.4.

### Steps to reproduce
1. Відкрити https://parabank.parasoft.com/parabank/index.htm у Chrome, нова сесія (інкогніто), без входу.
2. У блоці «Customer Login» у поле **Username** ввести `nobody_zz_9174`.
3. У поле **Password** ввести `qq`.
4. Натиснути кнопку **Log In**.

### Actual result
Після кроку 4 відкривається сторінка overview.htm «Accounts Overview». Ліва колонка: «Welcome John Smith» і меню кабінету. Таблиця містить 9 рахунків (13344, 16119, 16230, 16341, 16452, 42537, 42648, 42759, 42870; Total $5022.93). Те саме відбувається для `galtechfintech` / `wrong_pass123`.

### Expected result
Після кроку 4 вхід не виконується; показано сторінку з повідомленням «Логін або пароль не підтверджено» (F-20); ліва колонка містить блок «Customer Login» (GUI-10); дані будь-якого клієнта не показуються.

### Environment
Див. шапку. Без облікового запису. Відтворено 09.11.2026 тричі в інтервалі 20:40–20:43 UTC; після скидання даних demo о 21:21 UTC не відтворюється.

## BUG-002 — Оплата рахунку (Bill Pay) підтверджується як успішна, але сума не списується з рахунку

**Severity:** Critical  **Priority:** P3  **Status:** Rejected (не відтворюється)
**Linked:** test case TC-024; requirement F-80

> **Повторна перевірка 11.11.2026 (Run 2):** TC-024: Bill Pay 250.00 з рахунку 42870 → баланс 515.50 → 265.50, кошти списано. Дефект не відтворюється, тому звіт переведено в Rejected. Спостерігався лише 09.11.2026 до скидання даних demo.

### Description
F-80: після перевірки полів система списує суму з рахунку і показує «Платіж на користь <одержувач> на суму <сума> виконано». Мережевий запит `POST /parabank/services_proxy/bank/billpay?accountId=<рахунок>&amount=<сума>` повертає HTTP 200. Відтворено на чотирьох рахунках двох клієнтів: 44979 (250.00), 46089 (250.00), 43092 (100.00), 59853 (50.00 і 10.00).
Severity Critical: клієнт отримує неправдиве підтвердження фінансової операції, облік коштів розходиться з фактом (втрата даних про платіж). Priority P3: інші кейси не блокує.

Тобто дефект проявляється лише в певному стані даних спільного demo. Точну умову встановити не вдалося: для цього довелося б змінювати налаштування Admin Page, а це заборонено п. 5.4.

## BUG-003 — Переказ на суму, більшу за доступну суму рахунку-джерела, виконується; баланс стає від'ємним

**Severity:** Major  **Priority:** P2  **Status:** New
**Linked:** test case TC-022; requirement F-70 (також BL-40)

### Description
F-70: якщо сума перевищує доступну суму рахунку-джерела, показується «Недостатньо коштів», переказ не виконується, введені значення зберігаються. BL-40: переказ дозволено лише за amount ≤ balance. Фактично переказ виконується, а баланс рахунку-джерела стає від'ємним (овердрафт за 1.3 SRS). У Run 1: 200.01 з рахунку з 200.00 → −0.01; 500.00 з рахунку зі 100.00 → −400.00. Контрольне відтворення за кроками нижче — двічі, до і після скидання даних demo.
Severity Major: ключова перевірка переказу не працює, але перекази з допустимою сумою виконуються правильно (TC-020, TC-049). Priority P2: дефект блокує TC-050 (BL-75), бо відхиленої операції для перевірки не виникає.

### Steps to reproduce
1. Відкрити https://parabank.parasoft.com/parabank/index.htm у Chrome, нова сесія.
2. Зареєструвати клієнта (див. «Типові дані реєстрації»).
3. Натиснути **Open New Account**; тип `SAVINGS`, рахунок-джерело — А; натиснути **Open New Account**. Новий рахунок (далі — Б) має $100.00.
4. Натиснути **Transfer Funds**; Amount `100.01`; From account # — Б; to account # — А.
5. Натиснути **Transfer**.
6. Натиснути **Accounts Overview**.

### Actual result
Після кроку 5: «Transfer Complete! $100.01 has been transferred from account #<Б> to account #<А>.». Після кроку 6: рахунок Б — Balance −$0.01, Available $0.00.

### Expected result
Після кроку 5 переказ не виконується, показано «Недостатньо коштів» (англ. — «Insufficient funds»), значення 100.01 і обрані рахунки залишаються у формі. Після кроку 6 рахунок Б — $100.00 (F-70, BL-40).

## BUG-005 — Реєстрація приймає пароль коротший за 8 символів (7 символів)

**Severity:** Major  **Priority:** P3  **Status:** New
**Linked:** test case TC-008; requirement GUI-30 (також S-20)

### Description
GUI-30: пароль має містити від 8 до 64 символів, щонайменше одну літеру й одну цифру; інакше поряд із полем показується «Пароль не відповідає вимогам», обліковий запис не створюється. S-20 посилається на ці правила. Фактично пароль `mach1kN` (7 символів — граничне значення нижче мінімуму 8) приймається: обліковий запис створюється і виконується вхід.
Severity Major: вимога безпеки до паролів не виконується, у системі з'являються облікові записи зі слабкими паролями; сама реєстрація працює. Priority P3: інші кейси не блокує.

### Steps to reproduce
1. Відкрити https://parabank.parasoft.com/parabank/register.htm у Chrome, нова сесія.
