## BUG-001 — Вхід із неправильним паролем відкриває кабінет іншого клієнта (John Smith)

**Severity:** Critical  **Priority:** P3  **Status:** New (нестабільний: не відтворюється після скидання даних demo)
**Linked:** test case TC-014; requirement F-20 (також S-20)

### Description
F-20 (SRS 1.1): якщо пара логін/пароль не відповідає жодному обліковому запису, система показує сторінку з повідомленням «Логін або пароль не підтверджено», а вхід не виконується. Перевірено дві пари: `galtechfintech` / `wrong_pass123` (існуючий логін, хибний пароль) і `nobody_zz_9174` / `qq` (неіснуючий логін), а також ручним набором і заповненням через скрипт. Порожній пароль обробляється правильно: «Please enter a username and password.».
Severity Critical: стороння особа бачить чужі фінансові дані й може виконувати операції від чужого імені, тобто це серйозний витік даних і обхід автентифікації. Priority P3 за 4.13: подальше виконання кейсів не блокується.

**Відтворюваність: нестабільна.** До 21:17 UTC дефект відтворювався 3 з 3 разів (20:40–20:43 UTC). Після того як demo скинуло дані (09.11.2026 ≈ 21:17 UTC, рахунки почали нумеруватися з 13455), ті самі кроки дали правильний результат: о 21:21 UTC для `nobody_zz_9174` / `qq` показано «Error! The username and password could not be verified.», вхід не виконано. Тобто дефект проявляється лише в певному стані даних спільного demo. Точну умову встановити не вдалося: для цього довелося б змінювати налаштування Admin Page, а це заборонено п. 5.4.

### Steps to reproduce
1. Відкрити https://parabank.parasoft.com/parabank/index.htm у Chrome, нова сесія (інкогніто), без входу.
2. У блоці «Customer Login» у поле **Username** ввести `nobody_zz_9174`.

Контрольне відтворення за кроками нижче — двічі, до і після скидання даних demo.
Severity Major: ключова перевірка переказу не працює, але перекази з допустимою сумою виконуються правильно (TC-020, TC-049). Priority P2: дефект блокує TC-050 (BL-75), бо відхиленої операції для перевірки не виникає.
