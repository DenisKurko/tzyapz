## 1. Профіль компанії і продукту

**Компанія.** «ФінКит» — фінтех-компанія з Дніпра, працює з 2021 року. Вона розробляє й підтримує систему онлайн-банкінгу для регіонального банку, у якого близько 40 тисяч клієнтів — фізичних осіб. Команда розробки налічує 14 людей.

**Продукт.** Вебзастосунок, через який клієнт банку керує своїми грошима без візиту у відділення: реєструється, переглядає рахунки, відкриває нові, переказує кошти, оплачує рахунки, шукає транзакції, змінює контактні дані та подає заявку на кредит.

**Технології.**

| Шар | Технологія |
| --- | --- |
| Серверна частина | Java, Spring Boot |
| Інтерфейс | React |
| База даних | PostgreSQL |
| Інтеграція | захищений API до процесингового центру банку |

**Чому з'явився відділ якості.** Відділ створили після інциденту з подвійним списанням коштів при переказі. Для продукту, що працює з грошима, така помилка — не дрібниця: вона б'є по довірі клієнтів і по репутації банку.

**Регуляторний контекст.** Регулятор вимагає документованого тестування перед кожним релізом, тому «досьє якості» — обов'язкова частина випуску, а не формальність.

**Стратегія.** Головний напрям розвитку — кредитування онлайн, без відвідування відділення. Саме цьому присвячена нова функція із замовлення (розділ 4).

**Що це означає для тестувальника.**

- Найдорожчі помилки — у переказах, списаннях і розрахунках; на них варто звертати найбільше уваги.
- Ліміти, ставки й формули мають збігатися з тими, за якими реально працює банк, — «приблизних» значень бути не може.
- Поточна версія доступна для практики на demo-застосунку ParaBank. Він відтворює лише клієнтські функції, тому ролі операціоніста, ризик-менеджера й адміністратора існують лише в моделях процесів і user stories, а не в тестах.

## 2. Користувачі та ролі

| Роль | Що робить у продукті | Приклад із легенди |
| --- | --- | --- |
| **Клієнт** | Реєструється й входить, дивиться рахунки, відкриває нові, переказує кошти, оплачує рахунки, шукає транзакції, оновлює контакти, подає заявку на кредит | Андрій, фрилансер, щомісяця переказує гроші на ощадний рахунок |

| **Адміністратор** | Керує обліковими записами працівників, параметрами лімітів і тарифів, журналом аудиту | Оксана змінює денний ліміт переказів |

| Процесинговий центр | 2 «Переказ коштів» (окремий пул) |

### 3.2. Покриття вимог до набору моделей

| Вимога методички | Де виконується |
| --- | --- |
| 4 моделі (норматив для команди з 5 осіб) | Моделі 1–4 — усі чотири процеси легенди |
| ≥ 3 різні типи шлюзів | XOR за даними (усі моделі); XOR за подіями (М1 №5, М2 №4, М3 №19, М4 №4); паралельний ТА (М2 №14 розгалуження, №17 синхронізація) |
| ≥ 1 підпроцес | Згорнутий — «Перевірити документи клієнта» (М1 №10); розгорнутий — «Скоринг заявки» (М3 №13) |
| Три види подій + проміжні різних тригерів | Початкові — усі моделі; проміжні: повідомлення (М3 №4), таймер на межі дії (М3 №7, шлюз за подіями М3 №19), помилка на межі дії (М2 №15); кінцеві — усі моделі, у банківського пулу — по кілька різних на процес |
| Потоки повідомлень між пулами | М1: 4→8, 12/15/17→5; М2: клієнт↔банк↔процесинговий центр; М3: 3→10, 17/18→4; М4: 3→7, 15→18, 10/13/16→4 |
| Дія-компенсація | М2 №21 «Скасувати списання», прив'язана до події-помилки на межі №15 — саме цей сценарій і був причиною інциденту з розділу 1 |
| Артефакти даних | Об'єкти: «Заявка на рахунок», «Переказ», «Заявка на кредит», «Графік платежів», «Платіжне доручення»; сховища: «Реєстр рахунків», «Журнал транзакцій» |
| Анотації | М1 №19; М2 №25; М3 №20, №23; М4 №21 |
| Кожна доріжка має ≥1 дію | «Операціоніст» — М1 №10–11, М2 №12–13; «Ризик-менеджер» — М3 №15–16; «Система» — усі моделі |

Кожна таблиця нижче — «специфікація» моделі: за нею рецензент перевіряє типи елементів, а інженер будує діаграму. Умовні позначення: **XOR** — виключне АБО; **ТА** — паралельний шлюз (термін методички, п. 4.5); «задача + кидальна подія» — крок, після якого учасник надсилає повідомлення; «→ до N» — потік веде до елемента №N, зокрема через межу пулу як потік повідомлень.

## 4. Замовлення на нову функцію й очікування

### 4.1. Що просить керівництво

Керівництво «ФінКит» хоче, щоб клієнти могли дізнатися умови кредиту ще до візиту у відділення. Для цього потрібні кредитний калькулятор і онлайн-заявка: клієнт сам рахує платіж, бачить графік платежів і одразу отримує попереднє рішення. Головна вимога — точність: ліміти й формули мають збігатися з тими, за якими працює банк, жодних приблизних цифр.

Нова функція розширює процес 3 «Оформлення кредиту»: до існуючої заявки додаються розрахунок і графік до її подання, а також видимість статусу після подання.

### 4.2. Очікування замовника

Кожному очікуванню присвоєно код, за яким його простежуватимуть user stories в аркуші «Очікування → stories».

| Код | Очікування (своїми словами) | Хто зачеплений |
| --- | --- | --- |
| О-1 | Клієнт вводить суму, строк у місяцях і ставку та одразу бачить щомісячний платіж за ануїтетною схемою й загальну переплату | Клієнт |
| О-2 | Калькулятор показує графік за місяцями: дата, частина тіла кредиту, відсотки, залишок | Клієнт |
| О-3 | Система не приймає суму, строк чи ставку поза лімітами банку і пояснює причину | Клієнт |
| О-4 | Заявку можна подати прямо з калькулятора; попереднє рішення з'являється за кілька секунд | Клієнт |
| О-5 | Ризик-менеджер бачить заявки, що потребують ручного розгляду, разом із результатом скорингу | Ризик-менеджер |
| О-6 | Клієнт бачить статус заявки в кабінеті й отримує повідомлення про його зміну | Клієнт |

### 4.3. Що змінюється для кожної ролі

Беклог має охоплювати всі ролі, для яких функція щось змінює, тож пройдімо всі ролі легенди.

| Роль | Що змінюється | Очікування |
| --- | --- | --- |
| Клієнт | Основний користувач: рахує, вибирає умови, подає заявку, стежить за статусом | О-1, О-2, О-3, О-4, О-6 |
| Ризик-менеджер | Отримує заявки на ручний розгляд разом зі скорингом | О-5 |
| Операціоніст | Прямої вимоги немає; чи бере він участь у новому процесі — те саме відкрите питання, що й для моделі процесу (див. 3.7, п. 1) | — |
| Адміністратор | Прямої вимоги в замовленні немає, але легенда описує його роль як «керує... параметрами лімітів і тарифів» (п. 4.2 каталогу) — саме він, за логікою цього опису, і налаштовує ліміти суми/строку/ставки, які перевіряє калькулятор | О-3 (непрямо) |

### 4.4. Вимоги, що впливають на тестування

- **Точність розрахунків.** Платіж рахується за ануїтетною формулою; результат має збігатися з банківським до копійки.
- **Ліміти.** Суму, строк і ставку потрібно перевіряти на межах, а повідомлення про порушення — на зрозумілість.
- **Швидкість рішення.** Попереднє рішення має з'явитися за кілька секунд.
- **Повідомлення.** Зміна статусу заявки має бути помітною клієнту.
